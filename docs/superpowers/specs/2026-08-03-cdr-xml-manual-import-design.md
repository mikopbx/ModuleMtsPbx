# Выгрузка CDR в XML и ручная загрузка в 1С

## Цель

Подготовить автономный PHP-скрипт, который читает основную SQLite-базу истории звонков MikoPBX и формирует XML для загрузки в 1С. Создать отдельную версию существующей внешней обработки 1С, сохранив сетевую синхронизацию и добавив ручную загрузку сформированного XML-файла.

## Результаты

1. Автономный CLI-скрипт PHP без зависимостей от классов и библиотек модуля ModuleMtsPbx.
2. Новый EPF-файл с ручной загрузкой XML. Исходный `ЗагрузкаИсторииЗвонковMtsPBX_v1.epf` не изменяется.
3. Автоматические проверки экспортёра и проверка разборки/обратной сборки нового EPF.

## CLI экспортёра

Основной вызов:

```bash
php bin/exportCdrTo1C.php \
  --from="2026-07-16 20:55:11" \
  --output="/tmp/cdr-history.xml"
```

Параметры:

- `--from` — включительная нижняя граница по полю `start`; значение по умолчанию `2026-07-16 20:55:11`.
- `--output` — обязательный путь итогового XML-файла.
- `--database` — необязательный путь к SQLite; по умолчанию `/storage/usbdisk1/mikopbx/astlogs/asterisk/cdr.db`.
- `--help` — краткая справка без обращения к базе.

Скрипт использует только стандартные возможности PHP и PDO SQLite. Он проверяет параметры, существование и читаемость базы, доступность драйвера SQLite, схему исходной таблицы и возможность записи результата. Ошибки выводятся в STDERR, успешный итог — в STDOUT; ненулевой код завершения означает ошибку.

## Чтение CDR

Экспортируются строки основной таблицы CDR, для которых `start >= --from`. Точное имя таблицы определяется из поддерживаемых схем MikoPBX посредством проверки `sqlite_master` и `PRAGMA table_info`, а не жёсткого предположения без валидации. Обязательные поля проверяются до начала записи XML.

Строки читаются в стабильном порядке `linkedid`, `start`, `id`. Если `linkedid` пуст, идентификатор звонка берётся из `UNIQUEID`; строки без обоих идентификаторов пропускаются с итоговым счётчиком.

## Формат XML

Корневой элемент — `<history>`. Один `<history_record>` соответствует одному итоговому идентификатору звонка и содержит одну или несколько записей `<details>` для связанных плеч звонка. Это сохраняет многоэтапные звонки и исключает повтор нескольких `history_record` с одинаковым `entire_id`.

Используется формат, который уже разбирает обработка:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<history>
  <history_record no="..." entire_id="..." line="..." line_number="...">
    <details call_id="..." status="ANSWER" call_flow="" queue=""
             start="..." started="..." answered="..." finished="..."
             duration="..." conversation="..." record_file="..."
             finish_cause="Normal Clearing" />
    <from ext="" number="..." />
    <to ext="" number="..." />
  </history_record>
</history>
```

Для каждого `details` сразу следуют относящиеся к нему `from` и `to`. Статус `ANSWER` формируется для `disposition = ANSWERED`, иначе `CANCEL`. Временные значения `started`, `answered` и `finished` выдаются в RFC 3339 с часовым поясом системы; пустые даты остаются пустыми. Все значения XML-атрибутов экранируются.

XML записывается потоково во временный файл в каталоге назначения. После успешного завершения и закрытия документа временный файл атомарно переименовывается в заданный `--output`. При ошибке незавершённый файл удаляется, существующий итоговый файл не повреждается.

## Изменения обработки 1С

Новая версия обработки сохраняет существующие настройки `host`, `offset`, фоновую команду и сетевую синхронизацию.

В основной форме добавляется команда «Загрузить из XML». На клиенте она открывает стандартный диалог выбора файла с фильтром XML, асинхронно помещает выбранный файл во временное хранилище и вызывает серверную процедуру. Сервер читает текст как UTF-8, удаляет временные данные и передаёт XML в существующую `ОбработатьЗаписиИстории`, затем вызывает `ПроверитьОбработкуПропущенныхЗвонков`.

Ручной импорт выполняется в транзакции. При ошибке транзакция отменяется, пользователю показывается краткое описание, а подробности записываются в журнал регистрации. Успешный результат сообщает количество найденных групп звонков; `offset` и настройки сетевой синхронизации ручной импорт не изменяет.

Новый файл получает отдельное имя с версией `v2`; исходный EPF остаётся побайтово неизменным.

## Проверка

Для экспортёра создаются тесты на временной SQLite-базе:

- включительная фильтрация по дате;
- группировка нескольких плеч по `linkedid`;
- резервный идентификатор из `UNIQUEID`;
- корректное экранирование XML;
- преобразование статусов и пустых дат;
- ошибки параметров и несовместимой схемы;
- сохранность существующего output при ошибке.

Новый EPF разбирается после сборки через `v8unpack`; проверяются наличие добавленной команды и серверного пути импорта. Также выполняется контрольная сборка исходников нового EPF и сравнение декомпилированной структуры, поскольку бинарное представление контейнера недетерминировано.

## Ограничения

Автоматический запуск 1С на этом Mac не предусмотрен: платформа и тестовая информационная база отсутствуют. Поэтому проверка интерфейса и выполнения BSL ограничена структурной проверкой EPF; финальный запуск следует выполнить в целевой базе 1С.
